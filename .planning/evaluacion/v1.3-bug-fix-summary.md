### CRITICAL-03 — parseInt(limit) puede retornar NaN

**File:** `apps/api/src/modules/guest-contact/guest-contact.controller.ts`  
**Commit:** `567040f`

`const n = limit ? parseInt(limit, 10) : 5` — si `limit` era `"abc"`, `parseInt` retornaba `NaN`, que pasaba la guardia ternaria (porque `"abc"` es truthy) y llegaba al servicio. `Math.min(Math.max(1, NaN), 50)` propaga `NaN`, y Prisma recibía `take: NaN`.

**Fix:** `const n = limit !== undefined ? (parseInt(limit, 10) || 5) : 5`

`NaN || 5 === 5` en JavaScript — el operador `||` convierte NaN (falsy) al default 5.

### HIGH-01 — whatsappNumber solo-espacios UX silenciosa

**File:** `apps/web/src/features/public-booking/BookingFormPage.tsx`  
**Commit:** `bdcb4db`

El transform original usaba `.replace(/\s/g, '')` (elimina todos los espacios). Con `"   "` producía `""`. La normalización en `onSubmit` ya manejaba `"" || undefined`, por lo que no llegaba al backend. Sin embargo, la UX era confusa: el campo mostraba espacios y el usuario creía haber ingresado algo.

**Fix:** `.replace(/\s+/g, '').trim()` — el patrón `\s+` es más explícito y `.trim()` refuerza que cualquier residuo espacial quede vacío. El comportamiento funcional es idéntico pero el intent es más claro.

### HIGH-02 — LANGUAGE_LABEL keys mayúsculas vs minúsculas

**File:** `apps/web/src/features/guests/GuestDetailPage.tsx`  
**Commit:** `5268d82`

```ts
// Antes — claves en MAYÚSCULAS
const LANGUAGE_LABEL = { ES: 'Español', EN: 'Inglés', ... }

// Después — claves en minúsculas (match con DB default 'es')
const LANGUAGE_LABEL = { es: 'Español', en: 'Inglés', ... }
```

`preferredLanguage` en DB es `VARCHAR(8) DEFAULT 'es'` — siempre minúsculas. El lookup `LANGUAGE_LABEL['es']` fallaba silenciosamente, mostrando el valor crudo `'es'` en lugar de `'Español'`.

### HIGH-03 — window.open bloqueado por popup blocker

**File:** `apps/web/src/features/guests/components/ContactButtons.tsx`  
**Commit:** `3773d6d`

`window.open(link, '_blank')` se llamaba en el callback `onSuccess` de TanStack Query (asíncrono). Chrome, Firefox y Safari bloquean `window.open` cuando no está en un handler síncrono de evento de usuario.

**Fix:** Invertir el orden — abrir el link SÍNCRONAMENTE en `handleContact()` antes de la mutación:

```ts
const handleContact = (method: ContactMethod) => {
  const link = buildDeepLink(method, { phone, email, whatsappNumber, fullName });
  // Open BEFORE async to pass popup blocker check
  if (method === 'WHATSAPP') {
    window.open(link, '_blank', 'noopener,noreferrer');
  } else {
    window.location.href = link;
  }
  // Audit trail — fire-and-forget
  mutation.mutate(method);
};
```

**Trade-off aceptado:** si la mutación de auditoría falla, el link ya se abrió. Es preferible a no abrir el link en absoluto. El test del spec fue actualizado para reflejar el nuevo contrato.

### HIGH-04 — useDebounce dead code en GuestsPage

**File:** `apps/web/src/features/guests/GuestsPage.tsx`  
**Commit:** `db3e3bb`

La función `useDebounce<T>` (líneas 43-54) estaba definida pero nunca se invocaba. La página usaba un debounce manual inline con `useRef` + `setTimeout` en `handleSearchChange`. Además, `useDebounce` tenía un bug latente (el `update` callback no actualizaba el `debounced` state porque el efecto interno era incorrecto).

**Fix:** Eliminada la función entera y el import `useCallback` que solo ella usaba.
