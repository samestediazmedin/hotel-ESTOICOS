- **Public-facing form — input sanitization downstream**: All 6 fields flow to backend Zod validation (Plan 15-02). Frontend Zod is UX-only — never trust client-side validation alone. Already in place: backend rejects invalid E.164 with 400.
- **Marketing consent legal compliance (Ley 1581)**: Checkbox MUST be unchecked by default. Label MUST be the exact locked string. ANY pre-checked state or implied opt-in is a legal violation. Cannot be discretion.
- **whatsappNumber UX vs strict validation tension**: Users will naturally type `+57 300 123 4567` with spaces. Backend rejects this. Frontend strategy: `.transform(v => v?.replace(/\s/g, ''))` BEFORE regex check in Zod — allows the user readability and ensures the submitted value is canonical E.164.
- **<summary> Safari triangle visual bug**: Research §Pitfall #5. Mitigation: `[&::-webkit-details-marker]:hidden` + `list-none` classes on `<summary>`.
- **Form scope inflation**: BookingFormPage already has 7 required fields. Adding 6 visible fields would create cognitive overload. Mitigation: collapsed-by-default `<details>` keeps the form looking unchanged to users who don't need the extras.
- **XSS at form level**: React auto-escapes JSX text content. The two textareas pose no client XSS risk (React handles it). Backend escapeHtml (Plan 15-02 Task 2) handles email-side escaping.
</threat_model>
